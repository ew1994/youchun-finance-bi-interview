## 1. 一句话讲清逻辑

> **先确定企业采用哪种收入确认时点；系统按该时点筛出本期符合记账条件的订单，确认收入、成本和平台应收；再拿这批已入账数据去对平台结算、银行到账和财务总账，平账后才做经营分析。**

收入确认模式不是对账模式，而是记账的起点。它决定：
- 哪些订单进入本期；
- 本期确认多少收入、多少成本；
- 期末应收余额是多少；
- 后续结算和银行到账如何核销。

## 2. 四种收入确认模式

课程笔记给出四种可选口径，企业必须选择一种并保持期间一致。

| 模式 | 触发时点 | 本期可记账订单 | 优点 | 风险/适用范围 |
|---|---|---|---|---|
| 按订单时点 | 订单支付/成立 | 本期有效支付订单 | 与前端销售同步，数据最简单 | 未发货、取消、退款会造成收入虚高；适合无完善ERP的小商家 |
| 按发货时点 | 仓库发货 | 本期已发货订单 | 与出库和成本同步，ERP数据完整 | 确认收货前退款需冲回；要有可靠发货及成本数据 |
| 按账单时点 | 平台结算 | 本期实际结算订单 | 与平台实收接近，操作简单 | 收入滞后于业务，不适合做前端经营参考；平台到账不等于会计收入 |
| 按确认收货时点 | 买家或系统确认收货 | 本期完成确认收货的有效订单 | 最接近商品控制权转移，能降低未收货退款影响 | 依赖确认收货数据，收入晚于发货，需跟踪在途和售后 |

### 本作品选择：确认收货时点

理由：自营实物商品通过快递交付，确认收货是日常可取得、可批量验证的控制权转移证据，和订单、聚水潭发货、成本及平台售后能够形成完整证据链。

这是作品默认口径，不假设悠纯现行政策。入职后应先与财务经理确认；如果公司采用发货或账单口径，只切换`revenue_policy`规则，不重写对账流程。

不得在同一期间混用四种口径。管理口径可以另设，但必须与会计口径分名、可勾稽。

## 3. 可记账订单如何筛出来

### 3.1 筛选粒度

以**子订单**为最小记账单位，不用主订单。一个主订单可能包含多个商品、多个子订单和多个结算行。

### 3.2 筛选条件

确认收货口径下，本期可记账订单同时满足：

1. 支付成功，非未付款或支付失败；
2. 订单状态有效，排除取消、关闭、测试、刷单等无效单；
3. 确认收货时间落在本期：`period_start ≤ confirm_time < period_end`；
4. 聚水潭存在对应内部订单和实际出库；实物商品未发货不能确认收入；
5. 截至关账时点未被全额退款；部分退款按净额确认；
6. SKU、BOM、实际成本和平台应收科目已映射；
7. 同一子订单未被本批次或其他批次重复确认。

用代码表达：

```python
eligible = orders[
    (orders["pay_status"] == "已支付")
    & (~orders["order_status"].isin(["已取消", "交易关闭"]))
    & (orders["confirm_time"] >= period_start)
    & (orders["confirm_time"] < period_end)
    & (orders["invalid_flag"] == 0)
    & (orders["jst_order_id"].notna())
]
```

筛选结果要输出“**本期应记账订单池**”和“**排除订单及原因**”，不能只留下结果没有排除依据。

如果企业选择其他口径，只替换触发条件：

```text
按订单：pay_time 在期间
按发货：ship_time 在期间
按账单：settlement_time 在期间
按收货：confirm_time 在期间
```

### 3.3 记账金额

```text
商品对价（管理含税）
= 消费者实付＋平台承担补贴＋达人承担补贴
（商家优惠已体现在消费者实付中，不重复扣减）

初始确认收入
= 截至关账日的商品对价－已成功退款
－按会计政策预计的退货
（关账后发生的退款冲减退款发生期）

确认成本
= 聚水潭对应出库批次实际成本－可售退货冲回
```

平台服务费、达人佣金等属于费用，不直接冲减主营业务收入（企业作为主要责任人时）。平台净结算不是收入。

## 4. 一笔订单的时间线

以“山牛高钙两箱装送定制杯”为例：

| 日期 | 事件 | 财务处理 |
|---|---|---|
| 10-20 | 消费者支付84.80元，平台补贴5元 | 只形成订单，不确认收入 |
| 10-21 | 聚水潭审单并出库两箱奶＋定制杯，成本35元 | 形成履约和成本证据；未收货不确认收入 |
| 10-28 | 买家确认收货 | 满足本作品确认口径，确认收入、平台应收和销售成本 |
| 10-31 | 月末结账 | 平台应收毛额89.80元；按权责发生制计提平台费用27.74元，净应收62.06元 |
| 11-02 | 平台实际结算62.06元 | 计提与实际费用差额调整；结算62.06元核销净应收 |
| 11-03 | 提现到银行62.06元 | 钱包转银行；平台结算与银行到账完成闭环 |

关键结论：
- 10月确认收入，不能等到11月平台打款才确认；
- 10月末平台应收在账，11月结算只核销应收，不重复确认收入；
- 银行到账只影响资金，不影响10月收入；
- 未确认收货的已发货订单进入“发出商品/在途”，不进入本期收入；
- 确认收货后发生退款，冲减退款当期收入和成本，并追踪原订单。

## 5. 从记账到对账的完整流程

```text
抖店订单/售后
      ↓
选择收入确认政策 → 筛出本期可记账订单池
      ↓
匹配聚水潭审单、出库、赠品、退货与实际成本
      ↓
生成收入、成本、平台应收凭证
      ↓
平台结算明细：货款、补贴、退款、平台费、达人佣金
      ↓
应收核销 → 平台钱包 → 提现 → 银行到账
      ↓
财务ERP子账、总账、凭证勾稽
      ↓
异常闭环 → 期间锁定 → 经营分析
```

四段核对：

| 段落 | 核对内容 | 通过条件 |
|---|---|---|
| 记账订单池 | 本期应记账订单 vs 抖店订单、售后、聚水潭履约 | 订单只入账一次；已收货、已发货、成本完整；排除项有原因 |
| 平台应收 | 已入账收入/应收 vs 平台结算账单 | 货款、补贴、退款、平台费、达人佣金逐项一致；尾差≤0.01元 |
| 资金 | 结算批次 vs 钱包、提现、银行 | 结算净额＝钱包入账；提现与银行到账在窗口内一致 |
| 总账 | 平台应收、费用、成本 vs 财务ERP凭证和总账 | 应收余额为0、账面成本＝出库成本、子账＝总账 |

无法自动核销的进入异常：账实不符、重复入账、勾稽不平、金额尾差、退款跨期、费用差异。异常必须带源单、规则、金额、责任人和复检记录。

## 6. 输入、计算规则、输出

### 输入

| 类别 | 数据 |
|---|---|
| 平台 | 订单、售后、结算、待结算、资金流水、佣金和补贴 |
| 履约 | 聚水潭内部订单、审单、出库、物流、退货入库、批次成本 |
| 资金 | 平台钱包、提现、银行流水及回单 |
| 会计 | 财务ERP应收、收入、成本、费用凭证和余额 |
| 规则 | SKU/BOM、平台费率、达人佣金、账期、科目、容差、收入确认政策版本 |

### 计算规则

1. 订单号、SKU、金额和日期标准化；
2. 按收入确认政策筛选本期可记账订单；
3. 匹配聚水潭实际履约和成本；
4. 计算商品对价、收入、成本和平台应收；
5. 平台结算按子订单＋费用类型聚合后逐项核对；
6. 结算、钱包、提现、银行按批次勾稽；
7. 应收应付和总账按开放项/科目核销；
8. 差异按规则分类，正常在途观察，真实异常进入闭环。

### 输出

- 本期可记账订单池及排除清单；
- 收入、成本、平台应收明细；
- 平台结算、银行、总账对账底稿；
- 异常台账及闭环记录；
- 期间锁定后的经营指标和BI；
- 完整源文件、规则版本和操作审计。

## 7. 系统总体设计

### 7.1 一期落地方式：文件夹就是数据接口

一期不依赖平台或聚水潭API。财务按固定模板导出报表，放入指定批次目录，在低代码页面点击“运行对账”。

```text
inbox/
└─ 店铺ID/2026-10/RUN-20261031-001/
   ├─ manifest.yaml
   ├─ douyin/
   │  ├─ orders.csv
   │  ├─ aftersales.csv
   │  ├─ settlements.csv
   │  └─ funds.csv
   ├─ jst/
   │  ├─ orders.csv
   │  ├─ shipments.csv
   │  ├─ returns.csv
   │  └─ costs.csv
   ├─ bank/
   │  └─ statements.csv
   ├─ erp/
   │  ├─ ar_open.csv
   │  └─ vouchers.csv
   └─ master/
      ├─ sku_bom.csv
      ├─ fee_rules.csv
      └─ account_mapping.csv
```

`manifest.yaml`记录店铺、会计期间、关账时点、收入确认政策版本、各文件哈希和上传人。系统先将原始文件复制到只读原始层，再开始处理，任何人不能直接改原始文件。

文件夹输入不是简单“能读就行”，必须固定模板、字段名、数据类型和期间。文件缺失、重复、表头变化或控制总额不符时，批次直接停止并输出缺什么、找谁补，不继续生成错误结果。

## 8. 数据对象抽象

### 8.1 统一规则

- 订单号、SKU、达人ID按字符串处理，保留前导零；
- 金额统一转“分”的整数，禁止用浮点数做最终核销；
- 所有时间保留原值，同时生成统一时区和业务日期；
- 平台状态、售后状态、结算类型映射到公司标准码表；
- 每条标准记录保留`source_file`、`source_row`、`batch_id`和`run_id`。

### 8.2 五类源对象

| 对象 | 粒度 | 核心字段 |
|---|---|---|
| 平台订单/售后 | 子订单行、售后事件 | 主/子订单、店铺、SKU、数量、实付、商家优惠、平台/达人补贴、支付/发货/确认收货时间、订单状态、退款状态、流量来源、达人ID |
| 平台结算 | 结算行 | 结算行ID、子订单、结算批次、收入/费用类型、符号金额、计费基数、费率、结算时间、入账账户 |
| 聚水潭履约与成本 | 出库单行/退货行 | 线上订单号、内部订单号、出库单号、实物SKU、数量、批次、单位成本、出库时间、退货数量、质检状态 |
| 资金流水 | 钱包/银行流水行 | 流水号、来源账户、收支方向、金额、动账时间、提现批次、银行参考号、对方户名 |
| 财务凭证 | 凭证行 | 凭证号、来源业务号、科目、借贷方向、金额、过账期间、应收/应付余额 |

### 8.3 派生对象

| 对象 | 产生方式 | 关键字段 |
|---|---|---|
| `RevenueFact` | 按政策筛选可记账订单后生成 | 子订单、收入日期、含税对价、收入、税额、成本、应收 |
| `MatchResult` | 匹配引擎生成 | 左对象、右对象、匹配规则、规则版本、状态、置信度 |
| `ExceptionCase` | 差异规则生成 | 异常类型、差异金额、证据、责任人、状态、SLA |
| `WriteOffBatch` | 核销审批后生成 | 批次、核销明细、执行结果、回滚记录 |
| `MonthlyAnalysisFact` | 锁定期间按子订单、链接和 SKU 聚合 | 期间、维度键、净实销、退款、成本、毛利、贡献利润、来源批次 |
| `ExpenseAllocationFact` | 费用直接归属及公共费用分摊后生成 | 费用来源单、原始金额、归属对象、分摊基数、比例、规则版本、审批人 |
| `CashPositionFact` | 平台应收、钱包、提现和银行流水勾稽后生成 | 资金环节、期初、本期增减、期末、账龄、在途状态、来源流水 |

派生对象都可以回到源文件和源行，不能只有汇总数。

## 9. 对账引擎设计

### 9.1 运行流水线

```text
校验批次
→ 标准化对象
→ 按收入政策生成可记账订单池
→ 匹配聚水潭履约和成本
→ 生成收入、成本、应收
→ 匹配平台结算和费用
→ 匹配钱包、提现、银行
→ 匹配财务ERP应收及凭证
→ 差异分类
→ 人工补证/调整
→ 重跑复检
→ 自动/人工核销
→ 锁定期间
→ 生成财务分析
```

### 9.2 对账规则抽象

每条规则都配置为：

```text
规则 = 左对象 + 右对象 + 关联键 + 金额口径 + 时间窗口 + 容差 + 异常动作
```

| 编号 | 左对象 | 右对象 | 关联键 | 通过条件 |
|---|---|---|---|---|
| M01 | 可记账订单/收入事实 | 聚水潭出库与成本 | 子订单号、线上订单号 | 已发货、数量一致、批次成本完整、无重复 |
| M02 | 收入事实/平台应收 | 平台结算明细 | 子订单＋费用类型 | 货款、补贴、退款、平台费、达人佣金逐项一致，尾差≤0.01元 |
| M03 | 平台结算批次 | 钱包流水 | 结算批次 | 结算净额＝钱包入账 |
| M04 | 提现批次 | 银行流水 | 提现批次＋银行参考号 | 金额一致；窗口内为在途，超期为异常 |
| M05 | 平台应收/费用/成本 | 财务ERP凭证及总账 | 子订单、来源键、科目、期间 | 应收余额为0、成本一致、子账＝总账 |
| M06 | 应付发票/入库 | 供应商付款 | 采购单、入库单、发票号、付款号 | 数量、金额、税额、付款与红冲一致 |

M01-M05是本次抖音场景的核心；M06由同一引擎扩展，不与订单逻辑混在一起。

### 9.3 匹配算法

1. 文件哈希及业务唯一键去重；
2. 唯一键精确匹配；
3. 一对多先聚合：结算先按子订单＋费用类型汇总，再与应收比较；
4. 多对多按批次控制总额，不强行逐笔配对；
5. 无唯一键时只生成候选，必须人工确认；
6. 匹配结果保存左ID、右ID、规则版本、金额和证据，不允许覆盖历史。

### 9.4 异常分类

| 一级分类 | 典型规则 | 自动动作 |
|---|---|---|
| 数据不完整 | 文件缺失、字段缺失、SKU/BOM未映射 | 阻断批次，生成补数任务 |
| 账实不符 | 已确认收入但无出库、数量不符、成本缺失；银行未达 | 正常在途观察，超期异常 |
| 重复入账 | 文件哈希重复、结算行重复、凭证来源键重复 | 保留一条，冲销或作废重复记录 |
| 勾稽不平 | 应收余额≠0、子账≠总账、成本≠出库成本 | 追源单和凭证，提交调整 |
| 金额尾差 | 单笔≤0.01元且来源可解释 | 容差内标记复检，超容差转异常 |
| 退款/费用差异 | 退款、补贴扣回、佣金返还、跨期结算 | 关联原单和费用，调整或申诉 |

异常必须包含：`异常ID、规则、子订单/批次、差异金额、证据、责任部门、SLA、当前状态、处理记录`。

状态：`待处理→已分派→处理中→待复检→已关闭`；处理后重新运行规则，仍不平不能关闭。

### 9.5 自动核销闸门

```text
唯一匹配
＋金额在容差内
＋证据完整
＋无未决异常
＋科目映射已审批
＋权限和幂等检查通过
```

全部满足才自动核销；否则只生成核销建议，由财务复核。核销批次必须可回退，重复执行不能重复入账。

### 10.3 月度经营分析中心（课程第19课扩展）

在对账与关账之后新增“月度经营分析中心”，由**月度经营、费用分析、毛利分析、现金流分析**四个子模块组成。模块遵循课程“收入－成本－费用＝利润”的底层逻辑，并把店铺汇总继续下钻到商品链接和 SKU。

模块回答四个经营问题：

1. 本月卖了多少、退款多少、真实成交质量如何；
2. 钱花在哪里，哪些费用率异常，费用是否有原始账单支撑；
3. 哪些商品和链接真正赚钱，扣除推广及分摊费用后还剩多少贡献；
4. 利润是否已经变成现金，资金停在平台应收、钱包、提现在途还是银行未达。

#### 统一分析口径

- **期间**：默认自然月，支持月度、环比和累计视图；月中数据必须标记“本月截至某日”，不能直接包装成完整月环比。
- **粒度**：店铺汇总以子订单为最小事实粒度，单品分析以`商品ID/链接ID＋SKU`为维度；同一商品对应多个链接时先按链接核算，再汇总到 SKU。
- **维度**：月份、店铺、渠道、商品链接、SKU、温层、达人、活动和流量来源。
- **销售口径**：剔除取消、关闭、测试、重复和刷单等无效记录；退款只统计成功退款，并区分未发货退款、已发货退款、退货退款和部分退款。
- **收入口径**：管理净实销与会计确认收入分列展示并保留勾稽，不用平台净结算替代收入。
- **成本口径**：使用聚水潭实际出库总成本，不用“单品标准成本×原始订单数量”代替；可售退货冲回成本，不可售退货和仅退款按经审批的报损政策处理。
- **费用口径**：平台费用以资金账单实际扣款为依据，推广费以推广后台实际消耗为依据，物流和包装以履约及供应商账单为依据，线下费用以 ERP 为依据。
- **现金口径**：销售归属期、平台结算期和银行到账期分别保留；现金流分析按实际资金动账日期统计，不回写改变销售所属月份。
- **发布口径**：未锁定期间只能形成分析草稿；正式月报必须记录`run_id`、规则版本、分摊版本、关账时点和数据截至时间。

#### 核心计算关系

```text
有效销售数量 = 销售数量 - 成功退款数量 - 无效/刷单数量
管理净实销 = 商品对价 - 成功退款 - 按政策预计的退货（如适用）
客单价 = 管理净实销 / 有效主订单数
退款率 = 成功退款金额 / 商品对价 × 100%

实际销售成本 = 实际出库成本 - 可售退货冲回成本
商品毛利 = 管理净实销 - 实际销售成本
商品毛利率 = 商品毛利 / 管理净实销 × 100%
履约后毛利 = 商品毛利 - 包装成本 - 物流成本

单品贡献利润（管理口径）
= 履约后毛利 - 平台服务费 - 达人佣金 - 运费险
- 推广费 - 其他直接归属费用 - 分摊费用

店铺经营利润（管理口径）
= Σ单品贡献利润 - 未分摊的线下公共费用
费用率 = 费用金额 / 管理净实销 × 100%
```

商品对价已经包含平台或达人承担的优惠时，不得再把同一笔补贴加进收入。平台服务费、达人佣金等已在平台净结算中扣除，也不能在现金流入中重复扣减。上述“单品贡献利润”和“店铺经营利润”是管理指标，不等同于法定净利润；税费、折旧及其他未纳入项目必须单独说明。

### 10.4 四个子模块功能设计

#### A. 月度经营分析

| 功能区 | 指标与展示 | 下钻证据 |
|---|---|---|
| 月度总览 | GMV、支付金额、商品对价、管理净实销、确认收入、销售成本、商品毛利、贡献利润 | 月度事实表、收入事实、成本事实 |
| 成交质量 | 有效订单数、有效销售数量、客单价、退款金额、退款率、无效订单排除金额 | 子订单、售后事件、排除原因 |
| 趋势与结构 | 日/周/月趋势，渠道、SKU、链接、达人、活动、温层销售及利润占比 | 统一维度键与来源业务号 |
| 环比解释 | 销售、退款、成本、费用、毛利和贡献利润变动额；区分完整月与月中口径 | 两期同版本指标及差异明细 |
| 经营问题清单 | 高退款、低客单、销量增长但贡献下降、负毛利商品 | 对应订单、商品和费用明细 |

环比不能只给红绿箭头，必须能拆解为“销售规模、退款、成本、平台/达人费用、推广费、线下费用”等变动因素。赠品链接出现负毛利时单独标识业务属性，不直接当作数据错误。

#### B. 费用分析

费用分为四层，避免所有支出混成一个总数：

| 费用层级 | 主要项目 | 归属方式 |
|---|---|---|
| 平台交易费用 | 平台服务费、达人佣金、运费险、支付或月付相关费用 | 优先按子订单和结算行直接归属 |
| 履约费用 | 包装、物流、仓储、冷链、报损 | 按出库单、物流单、批次或 SKU 归属 |
| 推广费用 | 千川、达人推广、活动及其他广告消耗 | 按推广记录直接匹配商品链接；无法直接匹配的再分摊 |
| 线下及公共费用 | 房租、水电、人员工资、共用服务费等 | 店铺层列示；管理需要时按审批规则分摊 |

费用分摊遵循以下规则：

1. **直接归属优先**：能定位到子订单、链接或 SKU 的费用，不参与公共分摊。
2. **公共费用只分一次**：默认按管理净实销占比分摊，也支持经审批的固定比例、订单量或销量分摊；同一费用不得同时使用多种方法重复扣除。
3. **保留分摊版本**：记录费用来源、原始金额、分摊基数、比例、舍入差、规则版本和审批人；分摊后合计必须等于原始待分摊金额。
4. **异常单独提示**：零或负净实销链接不自动强行分摊，转人工指定规则；退款导致的费用返还、佣金差异和补贴未达分别关联 R04、R05、R08、R09。
5. **同时看金额与费用率**：输出平台费用率、达人佣金率、推广费占比、物流费用率、总费用率及环比变化，支持定位到原始扣费或消耗记录。

#### C. 毛利与单品利润分析

页面依次展示“店铺 → 商品/SKU → 商品链接 → 子订单”四层，核心字段包括：

`销售数量、退款数量、有效销售数量、管理净实销、实际销售成本、商品毛利、商品毛利率、包装成本、物流成本、平台费用、达人佣金、推广费、分摊费用、单品贡献利润、贡献利润率`。

提供两张核心视图：

- **毛利桥**：管理净实销 → 商品成本 → 商品毛利 → 包装/物流 → 平台及达人费用 → 推广费 → 公共费用分摊 → 单品贡献利润。
- **单品利润表**：按 SKU 和链接排序，标识负毛利、低毛利、高推广、高退款和高报损项目，并能回到订单、售后、出库成本及费用账单。

管理分析必须区分“商品毛利”和“单品贡献利润”。前者只扣实际销售成本，后者继续扣可归属费用与分摊费用；二者不能都简称为净利润。佣金率或推广费调整可做敏感性测算，但测算值只作为方案，不回写已锁定事实。

#### D. 现金流与资金占用分析

现金流模块不把权责发生制利润直接当成现金，也不替代法定现金流量表。按资金停留位置展示：

| 资金环节 | 核心指标 | 核对关系 |
|---|---|---|
| 平台应收 | 本期新增应收、已结算核销、正常未达、超期未结算 | 期初应收＋本期新增－本期核销±调整＝期末应收 |
| 平台钱包 | 已结算未提现、钱包入账、提现出账 | 平台结算批次与钱包流水勾稽 |
| 提现在途 | 已发起未到账、正常在途、超期在途 | 提现批次＋银行参考号勾稽 |
| 银行到账 | 本期实际到账、到账率、未达金额 | 银行流水与回单勾稽 |
| 采购及费用支出 | 采购付款、推广充值/消耗、物流付款、应付及到期支出 | 采购单、发票、付款单和费用单 |
| 特殊资金 | 周期购预收、受限资金、保证金 | 履约进度、银行及平台专项流水 |

核心公式：

```text
期末平台应收 = 期初平台应收 + 本期新增应收 - 本期结算核销 ± 经审批调整
期末提现在途 = 期初在途 + 本期发起提现 - 本期银行到账 ± 经审批调整
平台结算率 = 本期已结算核销金额 / 本期到期应结算金额 × 100%
提现到账率 = 已到账提现金额 / 已发起提现金额 × 100%（按提现批次归属期）
```

输出应收和应付账龄、正常跨期与超期异常、未来账期资金缺口预警，以及“利润增长但回款变慢”的联合提示。周期购预收款在收款与履约之间分开列示，不能因已收现金就提前确认全部收入。

### 10.5 月报输出与行动闭环

每月固定输出一份月度经营分析报告，顺序为：

1. 数据范围、关账状态、指标口径与未决数据缺口；
2. 月度经营总览及环比原因；
3. 费用结构、费用率与异常扣费；
4. SKU/链接毛利、贡献利润和负毛利清单；
5. 平台应收、钱包、提现在途、银行到账及资金缺口；
6. 经营行动表与下期验证结果。

行动表字段统一为：`问题、影响金额、证据链接、候选原因、建议动作、负责人、截止日、状态、下期验证指标、复检结论`。例如达人佣金率上升导致贡献利润下降，必须能回到具体结算行和佣金计划版本；调整后在下月同一口径验证，不用无法追溯的经验判断销项。

### 10.6 本模块验收标准

- 店铺汇总等于各 SKU 汇总，SKU 汇总可继续拆到链接和子订单；跨维度汇总不重复。
- 净实销、会计收入、平台结算和银行到账四个金额分别列示，并提供期间勾稽。
- 实际销售成本与出库、退货及报损记录一致；退款数量和金额不重复扣减。
- 直接归属费用与分摊费用之和等于费用源单金额，分摊前后总额一致且无重复扣除。
- 商品毛利、单品贡献利润、店铺经营利润按统一公式重算一致，零净实销时不直接输出误导性比率。
- 平台应收、钱包、提现在途和银行到账均满足期初、期末勾稽；正常在途不提前报错，超期自动进入异常中心。
- 任一汇总数均可下钻到源订单、售后、结算行、出库成本、推广记录、银行流水或 ERP 凭证。
- 未锁定期间只能发布草稿；正式月报保留批次、规则、分摊版本和操作审计。

核心筛选代码：

```python
def select_bookable_orders(order_snapshot, aftersales, period_start, period_end, policy):
    # order_snapshot 已把支付、发货、结算、确认收货时间及履约成本回填到子订单粒度
    date_field = {
        "order": "pay_time",
        "shipment": "ship_time",
        "settlement": "settlement_time",
        "receipt": "confirm_time",
    }[policy]

    refunds = (
        aftersales[aftersales["status"] == "退款成功"]
        .groupby("sub_order_id", as_index=False)
        .agg(refund_cents=("refund_cents", "sum"))
    )
    orders = order_snapshot.merge(
        refunds, on="sub_order_id", how="left", validate="one_to_one"
    ).fillna({"refund_cents": 0})

    eligible = orders[
        (orders["pay_status"] == "已支付")
        & (~orders["order_status"].isin(["已取消", "交易关闭"]))
        & (orders[date_field] >= period_start)
        & (orders[date_field] < period_end)
        & (orders["invalid_flag"] == 0)
        & (orders["jst_order_id"].notna())
        & (orders["cost_cents"].notna())
        & (orders["refund_cents"] < orders["consideration_cents"])
    ].copy()
    return eligible
```

生产版还需检查成本、全额退款、重复确认和科目映射。当前Node.js原型只展示流程；Python和SQL是目标实现，不宣称已在悠纯上线。

## 12. 验收标准

- 同一店铺、同一期间，完整人工工时降低≥60%；
- 异常闭环率≥95%，错误自动核销为0；
- 报表交付时效提升≥50%；
- 同一子订单不重复确认收入或重复生成凭证；
- 文件缺失、重复导入、一对多结算、赠品成本、退款跨期、银行在途均有测试；
- 任一指标都能回到源文件、源行、规则和凭证。

## 13. 面试讲解

> 我先确定收入确认时点，本作品默认确认收货。财务把抖店、聚水潭、银行和财务ERP报表放进固定批次目录，系统先校验文件和主数据，再抽象为订单、履约成本、结算、资金、凭证五类对象。按确认收货筛选出可记账订单池，生成收入、成本和平台应收；然后依次对履约、平台结算、银行资金和财务总账，异常分类闭环，最后只基于锁定数据出经营分析。
